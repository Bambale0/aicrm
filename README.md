# ЖКХ CRM

CRM для управляющей компании: приём и контроль заявок жителей, диспетчерская, сотрудники, подрядчики, объекты, подключаемые мессенджеры и роботизация.

## Основные модули

- **Заявки** — заявитель, адрес/помещение, категория, приоритет, SLA, исполнитель или подрядчик, история изменений.
- **Диспетчерская** — единый поток сообщений из подключённых каналов, ответ оператором и создание заявки из диалога.
- **Объекты и жители** — дома, помещения, жители и их контактные каналы.
- **Сотрудники и подрядчики** — роли сотрудников и список компаний-подрядчиков.
- **Каналы связи** — MAX как основной канал; Telegram и VK подключаются как дополнительные адаптеры к общей модели диалогов.
- **Автоматизация** — понятные правила «КОГДА → ЕСЛИ → ТО», собственные процессы, этапы, переменные, произвольные события и журнал выполнений.

Маркетинговых кампаний, продаж, полиграфического производства и старых demo-модулей в активном продукте нет.

## Автоматизация

Конструктор построен по одной схеме: **КОГДА событие → ЕСЛИ условия совпали → ТО выполнить действия**.

Можно автоматизировать встроенные сущности CRM — заявки, инциденты и диалоги — либо создать **свой процесс**. Свой процесс имеет этапы, любое количество одновременных запусков, произвольные JSON-переменные и собственные события. Правила и маршрутизация хранятся в БД, а не в коде.

Frontend не содержит собственного каталога событий/действий. Он получает метаданные из:

`GET /automation/catalog`

Основные API:

- `GET/POST /automation/processes`
- `GET/POST /automation/stages`
- `GET/POST/PATCH /automation/rules`
- `GET/POST /automation/instances`
- `POST /automation/processes/{id}/instances`
- `PATCH /automation/instances/{id}`
- `POST /automation/instances/{id}/events`
- `POST /automation/events/{entity_type}/{event_type}`
- `GET /automation/executions`
- `GET /automation/validate`

Действия выполняются по порядку. Изменение статуса, приоритета, этапа или переменных может породить следующее событие и запустить следующую цепочку правил; глубина цепочки ограничена `AUTOMATION_MAX_DEPTH` для защиты от циклов. Для безопасной проверки конфигурации поддерживается `dry_run`.

## MAX: чат УК и личные заявки

Контур MAX использует ту же модель автоматизации, что и Битрикс:

**ТРИГГЕР → УСЛОВИЯ → РОБОТЫ**

Входящее сообщение само по себе не создаёт заявку. Сначала адаптер MAX нормализует событие и сохраняет его в диспетчерскую. Затем ИИ анализирует последние сообщения диалога и выдаёт структурированное решение.

Для общего чата:
1. бот добавляется в чат и получает права администратора read_all_messages;
2. событие bot_added автоматически регистрирует chat_id как чат под наблюдением;
3. ИИ рассматривает контекст последних сообщений и отделяет бытовой разговор от реальной проблемы;
4. если проблема подтверждена, создаётся триггер conversation_problem_detected;
5. стандартные роботы создают/обновляют заявку и формируют alert оператору;
6. созданная заявка публикует обычный request_created, поэтому дальше на неё действуют любые правила заявок.

Для личного диалога MAX используется детерминированный intake-flow без LLM:
1. первое сообщение запускает короткий опрос;
2. бот последовательно спрашивает **ФИО → Адрес → Номер телефона → Что случилось**;
3. прогресс опроса хранится в БД и переживает рестарт backend;
4. после последнего ответа создаётся/обновляется житель, фиксируется дом, создаётся заявка со статусом `new` и alert диспетчеру;
5. жителю сообщается только то, что обращение передано диспетчеру — номер заявки до принятия не раскрывается;
6. в реестре заявок диспетчер использует переходы из backend-каталога: **Принять → Начать выполнение → Выполнить / Отменить**;
7. при статусах `accepted`, `in_progress`, `cancelled`, `done` жителю автоматически уходит сообщение в исходный диалог.

Тексты шагов опроса и уведомлений редактируются администратором в **Каналы связи → MAX → Настроить** и хранятся в настройках интеграции. Frontend получает поля и дефолты из backend-каталога, не дублируя бизнес-список в TypeScript.

Webhook остаётся идемпотентным по идентификатору события, поэтому повтор одного MAX update не продвигает опрос дважды и не создаёт вторую заявку.

MAX работает через Webhook. Подключение выполняется администратором в разделе **Каналы связи**: сохранить access token → **Проверить** → **Webhook** → **Включить**. URL webhook и webhook-secret формируются на backend, а token/secret хранятся только в зашифрованном виде и никогда не возвращаются в браузер.

MAX chat/channel ID — отдельные сущности CRM, а не значения в коде или JSON-настройках интеграции. Администратор может создать, изменить, включить/выключить и удалить канал, выбрать назначение (мониторинг, alerts оператора, исходящие публикации), проверить права MAX и отправить тестовое сообщение. Событие `bot_added` автоматически обнаруживает чат мониторинга, после чего он остаётся полностью управляемым из CRM.

Для ИИ-диспетчера должен быть настроен внешний OpenAI-compatible API в разделе **ИИ API**. Сейчас deployment может быть направлен на DeepSeek для тестирования; позже достаточно заменить AI_API_BASE_URL на собственный AI gateway.

## Мессенджеры

Общие точки интеграции:

- `GET /messengers/providers`
- `GET /messengers/intake/catalog`
- `POST /messengers`
- `POST /messengers/{id}/verify`
- `POST /messengers/{id}/webhook/register`
- `GET/POST/PATCH/DELETE /messenger-channels`
- `POST /messenger-channels/{id}/verify`
- `POST /messenger-channels/{id}/test`
- `POST /webhooks/messengers/{provider}/{id}`
- `GET /conversations`
- `GET/POST /conversations/{id}/messages`
- `POST /conversations/{id}/request`
- `GET /housing/request-statuses/catalog`
- `PATCH /housing/requests/{id}` — переход статуса + уведомление жителю

Бизнес-логика CRM работает с нормализованными `Conversation` / `Message`, а не с payload конкретного мессенджера.

## Доступ администратора

Даже если обычная CRM запущена с `AUTH_REQUIRED=false`, административный control plane не становится публичным. Разделы управления пользователями, MAX/Telegram/VK-интеграциями, channel/chat ID, provider secrets, webhook-secret и AI API требуют реальный JWT пользователя с ролью `admin`/superuser. В open-mode администратор входит через `/login`; сохранённая admin-сессия восстанавливается после перезагрузки.

## Конфигурация

Никаких production-значений в коде. Скопируйте `.env.example` в `.env` и задайте значения окружения.

```bash
cp .env.example .env
docker compose up -d --build
```

Публичный reverse proxy/TLS находится вне приложения и проксирует:

- `/` → frontend;
- `/api/` → backend с удалением префикса `/api`.

## Проверки

```bash
python -m py_compile $(find backend/src/aicrm -name '*.py')
docker compose build backend frontend
SMOKE_BASE_URL=http://127.0.0.1:9001 python3 scripts/smoke.py
```
