# ЖКХ CRM

CRM для управляющей компании: приём и контроль заявок жителей, диспетчерская, сотрудники, подрядчики, объекты, подключаемые мессенджеры и роботизация.

## Основные модули

- **Заявки** — заявитель, адрес/помещение, категория, приоритет, SLA, исполнитель или подрядчик, история изменений.
- **Диспетчерская** — единый поток сообщений из подключённых каналов, ответ оператором и создание заявки из диалога.
- **Объекты и жители** — дома, помещения, жители и их контактные каналы.
- **Сотрудники и подрядчики** — роли сотрудников и список компаний-подрядчиков.
- **Каналы связи** — provider-agnostic интеграции с нормализацией сообщений. Telegram реализован; новые провайдеры подключаются адаптерами.
- **Автоматизация** — понятные правила «КОГДА → ЕСЛИ → ТО», собственные процессы, этапы, переменные, произвольные события и журнал выполнений.

Маркетинговых кампаний, продаж, полиграфического производства и старых demo-модулей в активном продукте нет.

## Автоматизация

Конструктор построен по одной схеме: **КОГДА событие → ЕСЛИ условия совпали → ТО выполнить действия**.

Можно автоматизировать встроенные сущности CRM — заявки, инциденты и диалоги — либо создать **свой процесс**. Свой процесс имеет этапы, любое количество одновременных запусков, произвольные JSON-переменные и собственные события. Правила и маршрутизация хранятся в БД, а не в коде.

Frontend не содержит собственного каталога событий/действий. Он получает метаданные из:

`GET /automation/catalog`

Основные API:

- `GET/POST /automation/processes`
- `GET/POST /automation/stages`
- `GET/POST/PATCH /automation/rules`
- `GET/POST /automation/instances`
- `POST /automation/processes/{id}/instances`
- `PATCH /automation/instances/{id}`
- `POST /automation/instances/{id}/events`
- `POST /automation/events/{entity_type}/{event_type}`
- `GET /automation/executions`
- `GET /automation/validate`

Действия выполняются по порядку. Изменение статуса, приоритета, этапа или переменных может породить следующее событие и запустить следующую цепочку правил; глубина цепочки ограничена `AUTOMATION_MAX_DEPTH` для защиты от циклов. Для безопасной проверки конфигурации поддерживается `dry_run`.

## Мессенджеры

Общие точки интеграции:

- `GET /messengers/providers`
- `POST /messengers`
- `POST /messengers/{id}/verify`
- `POST /messengers/{id}/webhook/register`
- `POST /webhooks/messengers/{provider}/{id}`
- `GET /conversations`
- `GET/POST /conversations/{id}/messages`
- `POST /conversations/{id}/request`

Бизнес-логика CRM работает с нормализованными `Conversation` / `Message`, а не с payload конкретного мессенджера.

## Конфигурация

Никаких production-значений в коде. Скопируйте `.env.example` в `.env` и задайте значения окружения.

```bash
cp .env.example .env
docker compose up -d --build
```

Публичный reverse proxy/TLS находится вне приложения и проксирует:

- `/` → frontend;
- `/api/` → backend с удалением префикса `/api`.

## Проверки

```bash
python -m py_compile $(find backend/src/aicrm -name '*.py')
docker compose build backend frontend
SMOKE_BASE_URL=http://127.0.0.1:9001 python3 scripts/smoke.py
```

Правила разработки находятся в `AGENTS.md`.
